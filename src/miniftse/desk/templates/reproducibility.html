{{ incident.title }} {{ incident.status }}

Every number in this section is historical — the pre-fix, cross-platform comparison. It is not the state of the build above: the panel at the top of this page is the current, live comparison for the snapshot being served. The fix described here has shipped, and these figures are kept because a closed incident with its numbers intact is a stronger artefact than a tidy page.

Provenance. The figures below are as recorded in {{ incident.source }}. Unlike the re-pin numbers at the foot of this page — which were reproduced on this machine and can be re-derived from the committed golden master — the cross-platform comparison predates this repository's records and is reproduced here from that document rather than re-measured. Two platforms are needed to observe it and only one was available.

What happened

The golden master had been pinned on Windows. A rebuild on Linux from the same commit, the same config and the same synthetic inputs produced {{ incident.constituents_rebuild }} constituents at the {{ incident.review_date }} review where the pinned master had {{ incident.constituents_pinned }}. One security, one review, one band.

The index maths handled it perfectly, and that is what made it dangerous. level_continuity_bps at that review was {{ "%.1f"|format(incident.level_continuity_bps) }}: the divisor absorbed the constituent change exactly as a rebase is supposed to, so the published level did not jump and no validation rule fired. Nothing looked wrong on the day.

But a divisor that has absorbed a different set of constituents is a different divisor from then on. From {{ incident.review_date }} the two builds were no longer the same index computed twice — they were two indices. The divisor diverged by up to {{ incident.max_divisor_divergence_bps }}bp, and {{ incident.divergent_dates }} of {{ incident.total_dates }} dates carried a different constituent count. Below the 0.1bp golden tolerance on the levels, so CI stayed green; well above zero, which is what the number should have been.

Root cause

Two lines, plus a third carrying the same exposure that had not fired yet. Line numbers are as they were at the time of the incident; the current location of each is given alongside.

Band membership is defined on the cumulative share of free-float market cap, so a last-bit difference in the running sum is not confined to one security — it shifts the cumulative percentile of every name below it. All that is then needed is one security close enough to a cutoff, and the whole band boundary moves by one name.

{{ incident.conclusion }}

That is the generalisable lesson, and it is not really about floating point. The ground rules said "the top 70% by value" and left the boundary case undefined, so when two platforms disagreed there was no document to say which one was right. The arithmetic was deciding a question the methodology should have answered.

What shipped

  1. Deterministic summation. np.cumsum is gone. _exact_cumulative computes every prefix with Shewchuk exact partial sums — the algorithm behind math.fsum, kept open so the running total can be read after each element. Each prefix is the correctly rounded value of the exact sum, so it cannot depend on how the machine associated the additions.
  2. A total order. The old sort was stable but only partial, so two securities of exactly equal size ranked in whatever order the caller's dict happened to iterate. Ties now break on ascending security id.
  3. Quantisation to a documented precision. Cumulative percentiles are rounded to {{ incident.quantisation_decimals }} decimal places before any comparison against a cutoff or a buffer edge — four orders of magnitude above the noise floor of an exactly rounded sum, and eight orders below the smallest difference anyone would call material. The number is published in the code, in DECISIONS.md D-014 and in the ground rules, not just one of the three.
  4. The tie-break written down. Ground Rules 2.1.1: a security exactly on a cutoff belongs to the band that cutoff closes. Ground Rules 8.3: exactly one buffer width past a boundary is not more than one buffer width, so the incumbent is held. Both are now decisions the methodology makes, not accidents the arithmetic makes.

Proven by permutation tests in tests/test_index_maths.py::TestBandingDeterminism, not by inspection: the same universe presented in hundreds of different orders must produce bit-identical cumulative percentiles and identical bands, and a security placed exactly on a quantised cutoff must land on the documented side of it.

What the fix moved, and the second finding

The fix changed the parent index, so the golden master was re-pinned deliberately, in its own commit, with the reasoning in DECISIONS.md D-014. Content hash {{ repin.hash_before[:8] }} → {{ repin.hash_after[:8] }}. Re-pinning an index history is a recalculation event, and it is worth showing exactly how small a thing caused this one.

Replaying all {{ repin.reviews_replayed }} reviews of the reference history through both the old and the new band logic gives exactly {{ repin.band_changes }} differing assignment. Not the np.cumsum limb — the cumulative percentiles came out bit-identical before and after, which is what you would expect, because the incident at the top of this page needed two platforms to show itself and this is one machine.

It was the buffer edge: the line included in the fix on the grounds that it had the same exposure and had simply not fired yet. It had fired. At the {{ repin.review }} review, {{ repin.security }} was the smallest name in the universe, so its cumulative share was exactly {{ repin.cumulative_share }} — the last-ranked security's always is. The Small Cap boundary is {{ repin.boundary }} and the buffer is {{ repin.buffer_width }}, and {{ repin.boundary }} + {{ repin.buffer_width }} is exactly {{ repin.cumulative_share }}, so it sat exactly one buffer width out. But abs({{ repin.cumulative_share }} - {{ repin.boundary }}) evaluates to {{ repin.computed_distance }}, because {{ repin.boundary }} has no exact binary representation, so the old <= width was false and the security was dropped to {{ repin.was_band }} — out of the All Cap index entirely. Under Ground Rules 8.3 as now written it is held in {{ repin.now_band }}.

This was not a knife-edge, and it is worth being precise about that. {{ repin.computed_distance }} is not a value that varies between machines or runs — it is what IEEE-754 double arithmetic gives for that subtraction, every time, everywhere. The old comparison was false by construction: any Small Cap incumbent that was also the smallest name in the universe was dropped to Micro Cap, reliably, not occasionally.

What is rare is the configuration, not the arithmetic. It takes a Small Cap incumbent that is simultaneously the last-ranked name and would otherwise fall to Micro, which lined up once in {{ repin.reviews_replayed }} reviews. Left unfixed it was guaranteed to recur the next time it lined up — which is a materially worse defect than a coin-flip, because a coin-flip at least announces itself by giving two different answers to the same question.

One security, one review. The divisor rebased to absorb it exactly as it should — the levels moved {{ repin.level_move_bps }}bp — and the divisor is {{ repin.divisor_move_bps }}bp different from that review onward, across the final {{ repin.dates_affected }} of {{ repin.total_dates }} dates. The same shape as the cross-platform incident above, found on one machine, by fixing a line nobody had watched fail. That is the argument for fixing a defect class rather than a defect.

Recorded while fixing this, and deliberately not changed here: because {{ repin.boundary }} + {{ repin.buffer_width }} is exactly {{ repin.cumulative_share }}, the entire Micro Cap band lies within one buffer width of the Small/Micro boundary. That buffer therefore can never release anything — post-fix, a Small Cap incumbent is always held. That is a consequence of the band boundaries and buffer width the ground rules specify, not of this fix, and changing it would be a methodology change requiring consultation. It is noted here so the record does not imply the Small/Micro buffer does something it cannot.
